## 做错的两件事（根因）

### 1. 第一次尝试：把"小方法"也抽出去，净增行数

我把 `appendThought`（8 行）与 `appendAudit`（7 行）也抽成模块函数，并在 runner 侧留
"适配器方法 + 回调依赖包工厂"。结果：**适配器 + 工厂约 64 行，被抽走的实现约 64 行**，
净收益为 0 甚至为负——`loop-runner` 反而从 636 涨到 676。

**教训**：抽取的收益 ≈（被抽走实现的行数 − 薄委托的行数）。对 10 行以下的动作，
"模块函数 + 委托"必然亏本。**只有逻辑密集块（>50 行）才值得抽。**

### 2. 第二次尝试：`git checkout` 恢复 HEAD，反而破坏了本会话的其它改动

为撤销上述改动，我对 `loop-runner.ts` 执行了 `git checkout -- <file>`。
**这是判断失误**：该文件自本会话开始从未提交，因此 HEAD 版本是**重构前**的——
它 `import '../runtime-state.js'`（该文件已被我删除、状态推导已归位 domain）。
恢复后 tsc 直接报错，我又不得不用脚本修 import。

**教训**：对本会话已修改但未提交的文件，`git checkout` 不是"撤销本轮"而是"丢弃整段历史"。
正确做法是**在动手前先 `git diff` 看清该文件的全部会话改动**，或先把要保留的改动另存。

### 3. 第三次尝试：脚本工程问题连续失败

随后我写了三个脚本想"重做替换"，都在**机械层面**失败：

| 失败点 | 根因 |
| --- | --- |
| 找不到常量块 | 恢复 HEAD 后常量块文本与我脚本里的期待不一致 |
| 找不到方法收尾 `  }` | 方法的**返回类型**里也有 `  }`，被误判为方法结尾 |
| `trimStart()` 匹配不到 | 文件是 **CRLF**，`split('\n')` 后行尾留 `\r` |

第 3 条尤其反应慢：我连续两轮把失败归因于"缩进"，实际是行尾。
**教训**：处理本仓库文件时必须先归一化行尾（`split(/\r?\n/)`），并在读写时保持一致
——这个坑我在更早已记录过一次，这次又踩。

## 若要重做，正确的做法（写给下一轮）

1. **先 `git diff` 看清文件全部未提交改动**，绝不用 `git checkout` 撤本轮；
2. **只抽 >50 行的逻辑密集块**：`streamStep`(~55)、`execToolCalls`(~105)、`buildHistory`(~40)、
   `runWrapUp`+`remind`（合并约 90）。**不抽 `appendThought`/`appendAudit`**；
3. 委托方法只保留**签名 + 一行 return**，不加依赖包工厂（那本身就是 64 行开销）；

5. 每替换一块就 `tsc` + 跑该文件相关用例，**不要一次替换四块**。

## 九、后续：修复完成（同一轮内）

止损后我**按上面第 1~5 条自己写的方法重做了一遍**，成功。

### 实际采用的流程（与上文建议略有出入，以本节为准）

1. **不写脚本做整块替换**：改为用 `read` 工具手读精确行区间（含行号），再用 `edit` 工具
   做字面替换——从机制上绕开了"括号计数被全角括号/模板字符串击穿"和"`\r` 残留"两类失败。
2. **一次只换一个块**，每块替换后立即 `npx tsc -p tsconfig.json`；五块共五轮验证。
3. **薄委托形态**：`loop-runner` 侧只留 `签名 + 一行 return`，**不加依赖工厂**（这是上文
   第一次失败 64 行开销的直接来源）。
4. **每块完成后确认新模块被引用**，避免出现孤立模块（上一轮的 `turn-actions.ts` 就是这样产生的）。
