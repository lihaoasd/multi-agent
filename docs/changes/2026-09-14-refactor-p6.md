## 二、P6：把"loop 策略名不副实"如实写进文档

这是本次交互**最早讨论、也最该纠正**的一处文档与实现偏差。原文（`docs/design/agent-runtime.md` §3）
把 `direct`/`reflective`/`plan-execute` 描述为策略注册表 + 各自的执行编排；实际代码只有一个回合实现。

改动：

1. **`docs/design/agent-runtime.md` §3** 顶部加"实现现状"标注块，逐条对照"本节承诺 vs 代码实际"：

   | 承诺 | 实际 |
   | --- | --- |
   | 策略注册表（strategy → runner） | **不存在**，三条策略共用一个 `AgentLoopRunner` |
   | `direct` = 单轮一次模型调用 | 实为**无限轮工具循环**（安全阀：同工具+同入参+同结果连续 3 次） |
   | `reflective` = 生成→自查→修订 | **无 critique 调用**，只有一句提示词 |
   | `plan-execute` = 计划→逐步→验证 | 计划是**硬编码单步**且**无消费者**；不逐步 |
   | `maxIterations`/`stepModelOverride`/`toolBudget` | **无消费者**（`maxIterations` 只在 4 个角色 YAML 里躺着） |

   并在策略表加"现状"列，把通用参数标为"目标形态，当前无消费者"。
   原表格保留（改名"目标语义"），便于对照而非抹掉历史。

2. **`README.md` 已知边界**新增一条，用用户能懂的话说明：三条策略**没有执行编排差异**，
   差别只是一句提示词 + 一条硬编码 `plan` 事件；**角色真正的能力差异来自 `tools:` 白名单**。
   同时补一条"重构成果"摘要（分层规则/存储抽象/领域归位/超大文件收敛的数字）。

3. **明确不改行为**：文中写清"补齐需要：计划由模型结构化产出 → 每步回写 `stepIndex/status` →
   恢复时消费 plan 事件 → `maxIterations`/`toolBudget` 生效；这**改动行为**，属独立方案，
   不在本次纯重构范围内"。这与用户最初的决策（D3：不并入 loop 策略机制，仅如实标注）一致。

## 三、P4 剩余项「工具注册表去全局化」：评估后延后（记录理由）

`infra/tools/executor.ts` 有两处进程级可变状态：模块级 `registry` Map（:53）与
`runnerOverride` + `setCommandRunner()`（:224）。计划里 P4 写着"去全局化"，本轮评估后**决定不做**：

- `registerTool`/`listToolDefs`/`isRegistered`/`executeTool`/`setCommandRunner` 被**约 20 个测试文件**
  直接调用（`task-completion-m8p` 17 处、`task-board-m8m` 14 处、`workdir-edit-safety-m8q` 11 处…）；
- 改成实例注入会**波及这些测试的装配**，而本重构的硬约束是"测试断言一行不改"；
- 它不影响 P4 主目标（路由拆分、错误映射、"server 不得深入 application"均已交付并 promote 为 error）。

**记为待办**，需要一次独立小方案（含测试装配改法）。

## 四、`meeting-service` 为何本轮没能达标（判断与依据）

`meeting-service.ts` 从 702 降到 643，仍未达 400。我尝试抽 `respond`（78 行）后**放弃**，
依据是：它依赖 **7 个实例成员**（`get`/`append`/`store`/`emitLineup`/`onShed`/`onInvited`/`onOpen`/`onJoined`/`markJoined`），
抽出去要注入一个大对象，**耦合并未真正降低**，属于"为拆而拆"。

正确做法是**按职责重组**（例如把"成员回应与入会编排"整体移到 `meeting-attendance.ts`，
把 `emitLineup`/`markJoined`/`list` 一并迁走），那是一次中等重构，留给下一轮。
