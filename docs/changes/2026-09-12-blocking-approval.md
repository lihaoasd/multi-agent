# 2026-09-12 阻塞式审批：提交审批后角色停下，决定后带结果继续

## 需求/问题

用户："**审批也是没有阻塞，角色继续执行**，cmd_run → ✗ 命令退出码 1 …"
（同一条反馈里还提到"角色发起问题后依然继续工作"——经日志核对，**提问的阻塞是生效的**，见下）

## 一、先纠正"提问没阻塞"这一条（有日志证据）

`data/projects/p_mty2pw1qjv2a4y/sessions/u_architect_1.log.jsonl` 中提问那一回合的尾部：

```
seq 171 tool_call   task_update
seq 173 tool_result task_update ok
seq 175 tool_call   ask_user
seq 176 tool_result ask_user    ok
seq 177 turn_end                 ok      ← 提问后**立即结束回合**，没有任何后续工具调用
```

结论：`ask_user` 的挂起**是生效的**（提问后本回合就结束了）。
用户看到的"继续工作"来自两种情况：
1. **其它角色**在各自会话继续干活（团队是并行的，只有提问者本人被挂起）；
2. 那个角色是**先把活干完（edits → artifact_submit → task_update）最后才提问**——
   平台只能挂起"提问之后的步骤"，无法让模型"提前提问"。

针对第 2 点，本轮把提示词写死了纪律：**需要用户拍板/批准的事要先问再做**
（"ask_user 与需要审批的命令都会立即挂起本回合，所以不要先干完再来问"）。

至于"回答以对话消息回注"：这是设计如此——答复会以**用户消息**写进该角色会话并唤醒它继续，
既让角色拿到结构化答复，也保留审计痕迹（`【回答提问 q_…】共 N 个问题 …`）。

## 二、审批改为阻塞式（本轮真正的修复）

旧行为（`loop-runner`）：

```ts
result = { ok:false, code:'APPROVAL_PENDING', reason:'已提交审批 …；请向用户说明并继续其余工作' }
```

→ 角色**继续干活**；用户批准后 `resumeCommand` 执行了命令，但**结果没有回注给角色**（它根本不知道批没批）。

新行为：

1. **提交审批即挂起**：`APPROVAL_PENDING` 被 loop 视为挂起信号（与 ask_user 同一通道），
   本回合**立即结束**，工具结果写明「**本轮到此结束**：你在等用户批准；批准后平台会把执行结果回给你」；
2. **决定后回注并唤醒**（`POST /approvals/:apid/decide`）：
   - 批准 → 平台执行原命令 → 把 `执行成功：<stdout/摘要>`（或 `执行失败（code）：<reason>`）写回会话并唤醒角色继续；
   - 拒绝 → 写回「已被用户拒绝（原因：…）。不要重复申请该动作；请改用其他方式或向用户说明」并唤醒，
     避免角色一直干等或自行绕过；
   - 非 user 会话（会议）不回注，返回 `wakeError` 说明。
3. 团队状态：有待批审批时该角色显示「**等待你处理**」（`GET /agents` 原本就支持），
   决定后自动回到空闲/继续。
4. 审计与界面：`tool_result` 带 `approvalId`；前端把这行渲染成 **`cmd_run ⏸ 已提交审批，等你批准后继续`**
   （不再显示成 ✗ 失败）。

## 测试

新增 `tests/approval-blocking-m8v.test.ts`（4 例）：
1. 需要审批的命令 → 模型**只被调用 1 次**、工作目录没有产生"等审批时偷偷写的文件"、审批 pending、
   审计行 `code=APPROVAL_PENDING` 且带 `approvalId`、团队状态 `waiting`；
2. 批准 → 平台执行命令（fake runner 返回 stdout）→ 会话里出现「已获批准」+ **执行结果** + 「请继续你的任务」；
3. 拒绝 → 会话里出现「已被用户拒绝」+ 原因 + 「不要重复申请」；
4. 批准后团队状态不再是 `waiting`。

## 边界与后续

- 审批决定只唤醒**原申请会话**；若该会话已被删除/停用，返回 `wakeError` 并只落审批结果。
- 同一角色可以同时有多个待批审批（队列不合并）；批准顺序由用户决定。
- **已知取舍**：审批挂起后任务保持 `in_progress`（暂停而非完成）；如果用户长期不决定，角色就一直等。
  若需要"超时提醒/自动拒绝"，可作为下一步（尚未实现）。
