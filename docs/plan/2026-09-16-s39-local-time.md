# S39 方案：时间显示改用本地时间（trace 时间差了 8 小时）

> 日期：2026-09-16　类型：用户报告（"trace的时间显示不对"）　真源：`design/ui.md` §4、`prd.md` FR-30
> 关联：`docs/changes/2026-09-16-s39-local-time.md`、`docs/plan/development.md`

## 1. 需求

用户口径：**trace 里的时间显示不对。**

| # | 需求 | 验收 |
| --- | --- | --- |
| R1 | 详细日志（trace）每行的时间是**本地时间** | UTC+8 机器上，`2026-09-17T11:52:29.007Z` 显示 `19:52:29.007`（不是 `11:52:29.007`） |
| R2 | 同一处伤一起修 | 右栏任务列表的 `updatedAt` 也显示本地时间（原来是同一个切片写法） |
| R3 | 不伪造时间 | 缺失 → 空字符串；不可解析 → 原样返回（便于排查），不要给一个"看着对"的值 |
| R4 | 只改显示 | 事件落盘仍是 UTC ISO（`clock.now().toISOString()`），日志/导出/接口不动 |
| R5 | 一处真相 | 界面上的钟点格式化只有一份实现（纯函数，可单测） |

## 2. 根因

| 位置 | 原实现 | 问题 |
| --- | --- | --- |
| `web/src/lib/event-display.ts` `shortTime()` | `ts.slice(11, 23)` + `length < 23` 猜测 | 事件 `ts` 是 `clock.now().toISOString()`（**UTC**，`…T13:52:29.007Z`）。直接切片 = 把 UTC 当本地时间显示：**本机（UTC+8）整整差 8 小时**；另外 `length < 23` 这种"靠长度猜格式"对 `+08:00` 这类写法也不成立 |
| `web/src/pages/RightColumn.tsx` 任务列表 | `task.updatedAt.slice(11, 19)` | 同一处伤（任务更新时间也显示 UTC） |

S35 的用例把 `11:52:29.007` 当成期望值写进了断言——**把 bug 钉成了契约**，所以一直绿。

## 3. 关键决定

1. **本地时间，不是 UTC**：单用户本机平台，用户看的是自己的表；跨时区协作不在范围内（真要 UTC 会在界面标注时区）。
2. **抽一份纯函数** `web/src/lib/time-format.ts` 的 `localClock(ts, {withMs})`：`new Date(ts)` → `getHours/getMinutes/getSeconds/getMilliseconds`（本地）+ 补零；`withMs:false` 给任务列表用（`HH:MM:SS`）。`event-display.shortTime` 改为**委托**它，签名不变（调用方零改动）。
3. **不可解析就原样透出**：`new Date('不是时间')` → `NaN`，此时返回原串；缺失/空串返回 `''`。不抛错、不伪造。
4. **不引入日期库**：`Date` 的本地读数 + 补零足够（项目原则：不为一次性代码建抽象、不新增重型依赖）。
5. **测试要能真正抓住这个 bug**：断言"**同一时刻的不同时区写法必须渲染成同一个本地钟点**"（`Z` 与 `+08:00`）——这条与时区无关，旧实现给 `11:52` 与 `19:52` 两个答案，必然失败；另加"与 `Date` 的本地读数一致（不是 UTC 读数）"。

## 4. 实现步骤

- 新增 `web/src/lib/time-format.ts`（`localClock`）。
- `web/src/lib/event-display.ts`：`shortTime` 委托 `localClock`；补 import 与该处注释。
- `web/src/pages/RightColumn.tsx`：任务时间改用 `localClock(task.updatedAt, { withMs: false })`。
- 测试：新增 `tests/unit/web/time-format.test.ts`（5）；修正 `tests/unit/web/event-display.test.ts` 里被钉成 UTC 的 trace 头部断言（改为按 `Date` 本地读数计算期望）。
- 文档回写：`prd` **D42** + FR-30 补注、`ui.md` §4、`README.md`/`plan/development.md`/`testing/plan.md`、验收阶段清单加 `s39`。

## 5. 验证方式

| 层 | 手段 |
| --- | --- |
| 单测 | `time-format.test.ts`：同一时刻不同写法一致（**旧实现必红**）/ 与 `Date` 本地读数一致 / `withMs:false` 格式 / 缺失与不可解析 / 无时区串按本地解释 |
| 反证 | 旧实现下 `11:52:29.007Z` 与 `19:52:29.007+08:00` 渲染成两个值（已实测：`11:52:29.007` vs `19:52:29.007`，本机偏移 -480 分钟＝UTC+8） |
| 回归 | `npm test` 全绿 + `coverage` + `ratchet` + `typecheck`/`eslint` + `npm run build` |
| **用户点验** | ① 会话窗口切到「详细日志」，时间应与本机时钟一致（对照最后一条消息的当前时间）；② 右栏任务列表的时间同理 |

## 6. 风险

| 风险 | 对策 |
| --- | --- |
| 用户身处其它时区时"本地"含义不同 | 单用户本机平台，本地即用户所见；若将来要固定时区/显示时区后缀，改 `localClock` 一处 |
| 旧日志里的时间戳格式不一 | `Date` 解析 + 不可解析原样透出；`+08:00` / `Z` / 无时区三种写法都有用例 |
| 其它界面还有 UTC 切片 | 已全仓检索 `slice(11` / `toISOString`：仅剩本处两例，均已改；后续统一用 `localClock` |
